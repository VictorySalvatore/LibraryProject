## 1. Цели и задачи проекта
**Тема проекта:** Разработка информационной системы для автоматизации процессов учета книг, читателей и выдач в личной библиотеке.
**Цели проекта:**
1. Создать удобный графический интерфейс для работы с библиотечным фондом.
2. Реализовать бизнес-логику выдачи и возврата книг с контролем доступности.
3. Автоматизировать расчет штрафов за просрочку и формирование отчетов.
4. Обеспечить надежное хранение данных (в файле и реляционной базе данных).
5. Применить на практике изученные паттерны проектирования, принципы SOLID, ORM и юнит-тестирование.

## 2. Описание выполненного по теории лекций
Проект написан на языке **C#** с использованием технологии **Windows Forms** (платформа .NET Framework 4.7.2).

### 2.1. Основы ООП и SOLID
В проекте строго соблюдаются пять принципов объектно-ориентированного проектирования (SOLID):

*   **S — Single Responsibility Principle (Принцип единственной ответственности)**
    *Суть:* Каждый класс должен иметь только одну причину для изменения.
    *   **Где применено:** Классы `Book`, `Reader`, `Loan` (в `Models.cs`) отвечают **только** за хранение данных. Класс `LibraryManager` (в `Service.cs`) отвечает **только** за бизнес-логику. Класс `Form1` отвечает **только** за интерфейс. Класс `Logger` отвечает **только** за запись логов в файл.
    *   **Результат:** Изменение дизайна интерфейса не затрагивает логику выдачи книг.

*   **O — Open/Closed Principle (Принцип открытости/закрытости)**
    *Суть:* Программные сущности должны быть открыты для расширения, но закрыты для изменения.
    *   **Где применено:** Паттерн **Стратегия (Strategy)** для расчета штрафов. В `LibraryManager` есть переменная `_penalty` типа `IPenaltyStrategy`. Сейчас есть классы `NoPenalty` (без штрафа) и `ProgressivePenalty` (прогрессивный штраф).
    *   **Результат:** Если завтра понадобится добавить новый вид штрафа, мы **не будем менять** код `LibraryManager`. Мы просто создадим новый класс (например, `FixedPenalty`) и передадим его в менеджер.

*   **L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
    *Суть:* Объекты наследующего класса должны без проблем заменять объекты базового класса.
    *   **Где применено:** В иерархии исключений (`Exceptions.cs`). Мы везде ловим ошибки через `catch (LibraryException ex)`. При этом кидаем (`throw`) его наследников: `ReaderNotFoundException`, `DuplicateLoanException`. Программа работает корректно, так как наследники ведут себя предсказуемо.
    *   Также стратегии `NoPenalty` и `ProgressivePenalty` взаимозаменяемы в переменной типа `IPenaltyStrategy`.

*   **I — Interface Segregation Principle (Принцип разделения интерфейса)**
    *Суть:* Клиенты не должны зависеть от методов, которые они не используют.
    *   **Где применено:** В проекте нет одного огромного интерфейса. Вместо этого созданы узкоспециализированные интерфейсы: `ILibraryService` (для библиотеки), `IReport` (для отчетов), `IReportOutput` (для вывода текста), `IBookCsv` (для CSV), `IPenaltyStrategy` (для штрафов).
    *   **Результат:** Классу, который выводит отчет, не нужно реализовывать методы для работы с CSV.

*   **D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
    *Суть:* Зависимости должны быть основаны на абстракциях, а не на конкретных реализациях.
    *   **Где применено:** В файле `Form1.cs` главная форма объявляет переменную так: `private ILibraryService _m;`. Форма **не зависит** от конкретного класса `LibraryManager`. Она зависит только от **интерфейса**.
    *   **Результат:** Мы можем полностью переписать логику менеджера (например, сделать сохранение в облако вместо файла), но форма об этом даже не узнает, и её код не сломается.

*   **Инкапсуляция:** В классах `Book`, `Reader` и `Loan` (файл `Models.cs`) свойства доступны через геттеры и сеттеры. Изменение количества доступных книг (`Now`) происходит только через методы менеджера, что защищает данные от некорректного изменения извне.
*   **Наследование:** Кастомные исключения (`LibraryException` и его наследники) наследуются от системного класса `Exception` (файл `Exceptions.cs`).
*   **Полиморфизм:** Переопределен метод `ToString()` во всех моделях для красивого отображения в `ListBox`. В паттернах используются интерфейсы (`IPenaltyStrategy`, `IReport`), что позволяет подставлять разные реализации.

### 2.2. Порождающие паттерны
*   **Singleton (Одиночка):** Класс `Logger` (в `Patterns.cs`). У него приватный конструктор, и он гарантирует, что во всей программе будет только один экземпляр логгера. Используется для записи действий в файл `library.log`.
*   **Factory Method (Фабричный метод):** Класс `LibraryFactory` и его наследник `DefaultLibraryFactory`. Инкапсулируют создание объектов `Book` и `Reader`, чтобы бизнес-логика не зависела от конструкторов.
*   **Builder (Строитель):** Класс `LoanBuilder`. Позволяет пошагово собрать сложный объект `Loan` (Выдача), защищая от создания невалидных объектов (например, выдачи без книги).

### 2.3. Структурные паттерны
*   **Proxy (Заместитель):** Класс `CachedReport`. Выступает в роли «обертки» для `RealReport`. Кэширует результат расчета просрочек на 3 секунды, чтобы не пересчитывать тяжелый отчет при частых запросах.
*   **Adapter (Адаптер):** Класс `BookCsv`. Позволяет конвертировать список объектов `List<Book>` в строку формата CSV и обратно (используется при экспорте/импорте).
*   **Bridge (Мост):** Класс `OverdueBridgeReport` (Абстракция) и интерфейс `IReportOutput` (Реализация, через `MessageBoxOutput`). Это разделяет формирование текста отчета от способа его вывода на экран.

### 2.4. Поведенческие паттерны
*   **Strategy (Стратегия):** Интерфейс `IPenaltyStrategy` и его реализации `NoPenalty` (без штрафа) и `ProgressivePenalty` (прогрессивный штраф). Позволяет менять формулу расчета штрафа без изменения кода менеджера.
*   **Chain of Responsibility (Цепочка обязанностей):** Классы `BookCheck` и `ReaderCheck`. Реализуют цепочку проверок перед выдачей книги: сначала проверяется наличие книги, затем статус читателя.
*   **Iterator (Итератор):** Класс `LoansByReader`. Позволяет последовательно обходить список выдач конкретного читателя, скрывая внутреннюю структуру коллекции.

### 2.5. Работа с базами данных (ORM)
*   В проекте используется **Entity Framework 6** (подход Code First).
*   Создан класс контекста `LibraryDbContext`, унаследованный от `DbContext`. В нём объявлены `DbSet` для книг, читателей и выдач.
*   В классе `Models.cs` применены атрибуты маппинга (`[Table]`, `[Key]`, `[Column]`, `[ForeignKey]`).
*   Метод `SaveToDatabase()` в `Service.cs` использует `db.SaveChanges()` для сохранения данных в базу без написания SQL-запросов. При выходе из программы данные сохраняются в фоне (через `Task.Run`), чтобы не подвешивать интерфейс.

### 2.6. Тестирование
*   Создан отдельный проект `ДЗ.Tests` с использованием фреймворка **NUnit**.
*   Написаны юнит-тесты, проверяющие бизнес-логику в изоляции от интерфейса: проверка на дублирование УДК, корректное уменьшение/увеличение доступных книг при выдаче и возврате, проверка наличия просрочек. Тесты проходят успешно.

## 3. Как запустить и протестировать проект

### Требования к системе:
*   Visual Studio 2019 или 2022 (с установленной рабочей нагрузкой «Разработка классических приложений .NET»).
*   .NET Framework 4.7.2.
*   SQL Server LocalDB (устанавливается вместе с Visual Studio).

### Инструкция по запуску:
1. Откройте файл решения (`.sln`) в Visual Studio.
2. Нажмите клавишу `F5` (или кнопку «Пуск» на верхней панели). Проект соберется и запустится.
3. При первом запуске программа автоматически создаст тестовые данные и базу данных.

### Инструкция по запуску тестов:
1. В верхнем меню Visual Studio выберите **Тест** -> **Обозреватель тестов** (Test Explorer).
2. В открывшемся окне нажмите кнопку **«Запустить все»** (Run All).
3. Убедитесь, что все 6 тестов отмечены зелеными галочками.

## 4. Руководство по использованию

1. **Переключение режимов:** В верхней части окна есть выпадающий список. Переключайте его между режимами «Книги», «Читатели» и «Выдачи». Список на экране и подписи к полям ввода будут меняться автоматически.
2. **Добавление:**
   *   В режиме «Книги» заполните поля (УДК, Автор, Название, Год, Всего) и нажмите кнопку «Добавить».
   *   В режиме «Читатели» нажмите «Добавить» — откроется всплывающее окно для ввода ФИО, телефона и email.
3. **Выдача книги:** Перейдите в режим «Книги», выделите книгу в списке и нажмите кнопку «Выдать». В появившемся окне выберите читателя и срок выдачи.
4. **Возврат книги:** Перейдите в режим «Выдачи», выберите активную выдачу и нажмите кнопку «Вернуть».
5. **Просмотр отчета о просрочках:** Нажмите кнопку «Отчёт». Откроется окно, в котором будет указано, кто, какую книгу и на сколько дней просрочил, а также сумма штрафа (с использованием паттерна Стратегия).
6. **Сохранение данных:** При закрытии программы появится диалог с предложением сохранить изменения. Нажмите «Да», чтобы данные записались в бинарный файл `library.dat` и в реляционную базу данных.

## 5. Обоснование отсутствия паттерна Abstract Factory

Паттерн **Abstract Factory (Абстрактная фабрика)** в проекте не используется, и это обоснованное архитектурное решение:
1.  **Отсутствие семейств объектов:** Абстрактная фабрика нужна для создания взаимосвязанных семейств объектов (например, кнопок и окон для разных операционных систем). В нашей предметной области сущности `Book` и `Reader` независимы друг от друга.
2.  **Принцип KISS:** Внедрение этого паттерна стало бы избыточным усложнением кода (Overengineering). 
3.  **Достаточность Factory Method:** Использованный паттерн «Фабричный метод» полностью решает задачу создания объектов и легко расширяется при необходимости.
