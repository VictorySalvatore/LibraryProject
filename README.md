## 1. Цели и задачи проекта
**Тема проекта:** Разработка информационной системы для автоматизации процессов учета книг, читателей и выдач в личной библиотеке.
**Цели проекта:**
1. Создать удобный графический интерфейс для работы с библиотечным фондом.
2. Реализовать бизнес-логику выдачи и возврата книг с контролем доступности.
3. Автоматизировать расчет штрафов за просрочку и формирование отчетов.
4. Обеспечить надежное хранение данных (в файле и реляционной базе данных).
5. Применить на практике изученные паттерны проектирования, принципы SOLID, ORM и юнит-тестирование.

## 2. Описание выполненного по теории лекций

Проект написан на языке **C#** с использованием технологии **Windows Forms** (платформа .NET Framework 4.7.2).

### 2.1. Применение принципов SOLID

В проекте строго соблюдаются пять принципов объектно-ориентированного проектирования (SOLID):

*   **S — Single Responsibility Principle (Принцип единственной ответственности)**
    *Суть:* Каждый класс должен иметь только одну причину для изменения.
    *   **Где применено:** Классы `Book`, `Reader`, `Loan` (в `Models.cs`) отвечают **только** за хранение данных. Класс `LibraryManager` (в `Service.cs`) отвечает **только** за бизнес-логику. Класс `Form1` отвечает **только** за интерфейс. Класс `Logger` отвечает **только** за запись логов в файл.
    *   **Результат:** Изменение дизайна интерфейса не затрагивает логику выдачи книг.

*   **O — Open/Closed Principle (Принцип открытости/закрытости)**
    *Суть:* Программные сущности должны быть открыты для расширения, но закрыты для изменения.
    *   **Где применено:** Паттерн **Стратегия (Strategy)** для расчета штрафов. В `LibraryManager` есть переменная `penalty` типа `PenaltyStrategy`. Сейчас есть классы `NoPenalty` (без штрафа) и `ProgressivePenalty` (прогрессивный штраф).
    *   **Результат:** Если завтра понадобится добавить новый вид штрафа, мы **не будем менять** код `LibraryManager`. Мы просто создадим новый класс (например, `FixedPenalty`) и передадим его в менеджер.

*   **L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
    *Суть:* Объекты наследующего класса должны без проблем заменять объекты базового класса.
    *   **Где применено:** В иерархии исключений (`Exceptions.cs`). Мы везде ловим ошибки через `catch (LibraryException ex)`. При этом кидаем (`throw`) его наследников: `ReaderNotFoundException`, `DuplicateLoanException`. Программа работает корректно, так как наследники ведут себя предсказуемо.
    *   Также стратегии `NoPenalty` и `ProgressivePenalty` взаимозаменяемы в переменной типа `IPenaltyStrategy`.

*   **I — Interface Segregation Principle (Принцип разделения интерфейса)**
    *Суть:* Клиенты не должны зависеть от методов, которые они не используют.
    *   **Где применено:** В проекте нет одного огромного интерфейса. Вместо этого созданы узкоспециализированные интерфейсы: `LibraryService` (для библиотеки), `Report` (для отчетов), `ReportOutput` (для вывода текста), `BookCsv` (для CSV), `PenaltyStrategy` (для штрафов).
    *   **Результат:** Классу, который выводит отчет, не нужно реализовывать методы для работы с CSV.

*   **D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
    *Суть:* Зависимости должны быть основаны на абстракциях, а не на конкретных реализациях.
    *   **Где применено:** В файле `Form1.cs` главная форма объявляет переменную так: `private LibraryService m;`. Форма **не зависит** от конкретного класса `LibraryManager`. Она зависит только от **интерфейса**.
    *   **Результат:** Мы можем полностью переписать логику менеджера (например, сделать сохранение в облако вместо файла), но форма об этом даже не узнает, и её код не сломается.

### 2.2. Основы ООП
*   **Инкапсуляция:** В классах `Book`, `Reader` и `Loan` свойства доступны через геттеры и сеттеры. Изменение количества доступных книг (`Now`) происходит только через методы менеджера.
*   **Наследование:** Кастомные исключения наследуются от системного класса `Exception`.
*   **Полиморфизм:** Переопределен метод `ToString()` во всех моделях для красивого отображения в `ListBox`. В паттернах используются интерфейсы, что позволяет подставлять разные реализации.

### 2.3. Порождающие паттерны
*   **Singleton (Одиночка):** Класс `Logger` (в `Patterns.cs`). У него приватный конструктор, и он гарантирует, что во всей программе будет только один экземпляр логгера.
*   **Factory Method (Фабричный метод):** Класс `LibraryFactory` и его наследник `DefLibraryFactory`. Инкапсулируют создание объектов `Book` и `Reader`.
*   **Builder (Строитель):** Класс `LoanBuilder`. Позволяет пошагово собрать сложный объект `Loan` (Выдача).

### 2.4. Структурные паттерны 
*   **Proxy (Заместитель):** Класс `CachedReport`. Кэширует результат расчета просрочек на 3 секунды, чтобы не пересчитывать тяжелый отчет при частых запросах.
*   **Adapter (Адаптер):** Класс `BookCsv`. Позволяет конвертировать список объектов `List<Book>` в строку формата CSV и обратно.
*   **Bridge (Мост):** Класс `OverdueBridgeReport` (Абстракция) и интерфейс `ReportOutput` (Реализация). Разделяет формирование текста отчета от способа его вывода.

### 2.5. Поведенческие паттерны
*   **Strategy (Стратегия):** Интерфейс `PenaltyStrategy` и его реализации `NoPenalty` и `ProgressivePenalty`. Позволяет менять формулу расчета штрафа.
*   **Chain of Responsibility (Цепочка):** Классы `BookCheck` и `ReaderCheck`. Реализуют цепочку проверок перед выдачей книги.
*   **Iterator (Итератор):** Класс `LoansByReader`. Позволяет последовательно обходить список выдач конкретного читателя.

### 2.6. Работа с базами данных
*   В проекте используется **Entity Framework 6** (подход Code First).
*   Создан класс контекста `LibraryDbContext`, унаследованный от `DbContext`. В нём объявлены `DbSet` для книг, читателей и выдач.
*   В `Models.cs` применены атрибуты маппинга (`[Table]`, `[Key]`, `[Column]`, `[ForeignKey]`).
*   Метод `SaveToDatabase()` использует `db.SaveChanges()` для сохранения данных в базу без написания SQL.

### 2.7. Тестирование
*   Создан отдельный проект `ДЗ.Tests` с использованием фреймворка **NUnit**.
*   Написаны юнит-тесты, проверяющие бизнес-логику: проверка на дублирование УДК, корректное изменение доступных книг при выдаче и возврате, проверка наличия просрочек. (6 тестов, все проходят).

## 4. Руководство по использованию

Программа имеет интуитивно понятный интерфейс, который динамически меняется в зависимости от выбранного режима. Ниже приведена подробная пошаговая инструкция по всем основным сценариям работы.

### 4.1. Переключение режимов работы
В верхней части главного окна расположен выпадающий список (ComboBox). 
*   Выберите **«Книги»**, чтобы работать с книжным фондом.
*   Выберите **«Читатели»**, чтобы управлять базой читателей.
*   Выберите **«Выдачи»**, чтобы отслеживать, кто и какие книги взял.
*При переключении режима автоматически меняется содержимое списка на экране и подписи к текстовым полям (например, поле «Автор» превращается в «ФИО»).*

### 4.2. Работа с книгами
1.  Переключите режим на **«Книги»**.
2.  В правой части формы заполните поля: УДК (уникальный шифр), Автор, Название, Год издания и Общее количество экземпляров.
3.  Нажмите кнопку **«Добавить»**. Если книга с таким УДК уже существует, программа выдаст ошибку. В противном случае книга появится в списке слева.
4.  Чтобы **отредактировать** книгу, выделите её в списке, измените данные в полях и нажмите **«Обновить»**.
5.  Чтобы **удалить** книгу, выделите её в списке и нажмите **«Удалить»**.
6.  Если нужно найти книгу, начните вводить её название или автора в поле поиска (над списком).

### 4.3. Работа с читателями
1.  Переключите режим на **«Читатели»**.
2.  Нажмите кнопку **«Добавить»**. Откроется всплывающее окно.
3.  Введите ФИО, номер читательского билета, телефон и email. Нажмите «Сохранить». 
4.  *Валидация:* Программа проверит правильность ввода телефона и email с помощью регулярных выражений. Если формат неверный, появится предупреждение.
5.  Чтобы **изменить** данные читателя, выделите его в списке, отредактируйте поля справа и нажмите **«Обновить»**.
6.  Чтобы **удалить** читателя, выделите его и нажмите **«Удалить»**.

### 4.4. Выдача книги
1.  Переключите режим на **«Книги»**.
2.  Выделите в списке книгу, которую хотите выдать.
3.  Нажмите кнопку **«Выдать»**.
4.  В открывшемся окне выберите читателя из выпадающего списка и укажите срок выдачи в днях (по умолчанию 14 дней). Нажмите «Выдать».
5.  *Результат:* Количество доступных экземпляров книги уменьшится на 1. В режиме «Выдачи» появится новая запись.

### 4.5. Возврат книги
1.  Переключите режим на **«Выдачи»**.
2.  Найдите в списке нужную выдачу (можно ориентироваться по УДК книги и ID читателя).
3.  Выделите строку и нажмите кнопку **«Вернуть»**.
4.  *Результат:* Книга вернется в фонд (количество доступных увеличится на 1), а в списке выдач она получит статус «Returned» (Возвращена).

### 4.6. Просмотр отчета о просрочках и штрафах
1.  Нажмите кнопку **«Отчёт»** в нижней части окна.
2.  Откроется всплывающее окно, в котором будет сформирован список всех просроченных книг.
3.  Для каждой просрочки отображается: ФИО читателя, Название книги, количество дней просрочки и **сумма штрафа** (рассчитывается автоматически по прогрессивной шкале).
4.  В самом низу отчета выводится общее количество просроченных книг.

### 4.7. Экспорт и импорт данных (CSV)
*   Нажмите кнопку **«Сохранить CSV»**, чтобы выгрузить текущий список книг в текстовый файл (удобно для открытия в Excel).
*   Нажмите кнопку **«Загрузить CSV»**, чтобы загрузить книги из ранее сохраненного файла (например, чтобы восстановить резервную копию).

### 4.8. Сохранение данных при выходе
1.  При нажатии на крестик (закрытие окна) программа спросит: *«Сохранить изменения перед выходом?»*.
2.  Нажмите **«Да»**. 
3.  Программа сохранит все данные в бинарный файл `library.dat` (для быстрой работы) и в базу данных SQL (через Entity Framework).
4.  Если нажать «Нет», все изменения, сделанные за текущую сессию, будут потеряны.

## 5. Обоснование отсутствия паттерна Abstract Factory

Паттерн **Abstract Factory (Абстрактная фабрика)** в проекте не используется, и это обоснованное архитектурное решение:
1.  **Отсутствие семейств объектов:** Абстрактная фабрика нужна для создания взаимосвязанных семейств объектов (например, кнопок и окон для разных ОС). В нашей предметной области сущности `Book` и `Reader` независимы.
2.  **Принцип KISS (Keep It Simple, Stupid):** Внедрение этого паттерна стало бы избыточным усложнением кода.
3.  **Достаточность Factory Method:** Использованный паттерн «Фабричный метод» полностью решает задачу создания объектов и легко расширяется при необходимости.

## 6. Архитектура и структура проекта

Проект построен по принципу разделения ответственности (SOLID). Взаимодействие слоев происходит следующим образом:
**Пользователь -> Интерфейс (UI) -> Менеджер (Бизнес-логика) -> Модели (Данные) и База данных/Файл.**

### За что отвечает каждый файл:

*   **`Form1.cs` и `Form1.Designer.cs` (Представление/UI)**
    *   **Роль:** Отвечает за графический интерфейс.
    *   **Как работает:** Здесь описаны кнопки, списки и текстовые поля. Форма не выполняет сложных вычислений — она просто ловит клики пользователя и передает команды менеджеру (`LibraryManager`), а затем отображает полученные данные на экране.
*   **`Service.cs` (Менеджер / Бизнес-логика)**
    *   **Роль:** «Мозг» программы. Здесь описан интерфейс `LibraryService` и класс `LibraryManager`.
    *   **Как работает:** В этом файле прописаны все правила: как выдавать книгу (проверка наличия), как возвращать, как считать штраф. Также здесь находится код для сохранения и загрузки данных (в файл и базу данных).
*   **`Models.cs` (Модели / Сущности)**
    *   **Роль:** Описание того, из чего состоит библиотека.
    *   **Как работает:** Здесь находятся классы `Book` (книга), `Reader` (читатель) и `Loan` (выдача). У них есть только свойства (УДК, Автор, ФИО) и атрибуты для базы данных. Никакой сложной логики в них нет.
*   **`Patterns.cs` (Паттерны проектирования)**
    *   **Роль:** Реализация 9 изученных паттернов.
    *   **Как работает:** Здесь лежат вспомогательные классы, которые делают код гибким (например, `Logger` для логов, `LoanBuilder` для создания выдач, `CachedReport` для кэширования отчета).
*   **`Exceptions.cs` (Обработка ошибок)**
    *   **Роль:** Описание кастомных ошибок.
    *   **Как работает:** Вместо непонятных системных ошибок программа выдает понятные: `ReaderNotFoundException` («Читатель не найден») или `DuplicateLoanException` («Книга уже выдана»).
*   **`LibraryDb.cs` (ORM / Работа с БД)**
    *   **Роль:** Связующее звено с базой данных (Entity Framework).
    *   **Как работает:** Этот класс переводит наши C#-объекты (из `Models.cs`) в таблицы реляционной базы данных SQL и обратно.
*   **`FormAddReader.cs` и `FormIssueLoan.cs` (Дополнительные окна)**
    *   **Роль:** Модальные окна для ввода данных.
    *   **Как работает:** `FormAddReader` открывается при добавлении читателя. `FormIssueLoan` открывается при выдаче книги (чтобы выбрать читателя и срок).
*   **`App.config` (Конфигурация)**
    *   **Роль:** Файл настроек.
    *   **Как работает:** Здесь хранится строка подключения (Connection String) к базе данных.
*   **`LibraryTests` (Проект с тестами)**
    *   **Роль:** Отдельный проект для проверки бизнес-логики.
    *   **Как работает:** Здесь лежат тесты (NUnit), которые проверяют, что менеджер правильно выдает книги и считает штрафы, независимо от интерфейса.

### Как работает программа (Общий цикл)
1.  При запуске загружается главная форма (`Form1`). Она обращается к менеджеру (`Service.cs`), чтобы тот загрузил данные из файла или базы данных.
2.  Пользователь выбирает режим (Книги/Читатели) и нажимает кнопки.
3.  Форма вызывает нужный метод у менеджера (например, `m.AddBook(...)`).
4.  Менеджер проверяет данные, использует паттерны из `Patterns.cs` (например, `Logger` для записи действия в лог) и сохраняет изменения в списках.
5.  Менеджер генерирует событие `DataChanged`, которое перехватывает форма и обновляет список на экране.
6.  При закрытии программы менеджер сериализует данные в файл `library.dat` и сохраняет их в базу данных через `LibraryDbContext`.
