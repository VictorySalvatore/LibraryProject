## 1. Цели и задачи проекта
**Тема проекта:** Разработка информационной системы для автоматизации процессов учета книг, читателей и выдач в личной библиотеке.

**Цели проекта:**
1. Создать удобный графический интерфейс для работы с библиотечным фондом.
2. Реализовать бизнес-логику выдачи и возврата книг с контролем доступности.
3. Автоматизировать расчет штрафов за просрочку и формирование отчетов.
4. Обеспечить надежное хранение данных (в файле и реляционной базе данных).
5. Применить на практике изученные паттерны проектирования, принципы SOLID, ORM и юнит-тестирование.

## 2. Описание выполненного по теории лекций

Проект написан на языке **C#** с использованием технологии **Windows Forms** (платформа .NET Framework 4.7.2).

### 2.1. Применение принципов SOLID

В проекте строго соблюдаются пять принципов объектно-ориентированного проектирования (SOLID):

*   **S — Single Responsibility Principle (Принцип единственной ответственности)**
    *Суть:* Каждый класс должен иметь только одну причину для изменения.
    *   **Где применено:** Классы `Book`, `Reader`, `Loan` (в `Models.cs`) отвечают **только** за хранение данных. Класс `LibraryManager` (в `Service.cs`) отвечает **только** за бизнес-логику. Класс `Form1` отвечает **только** за интерфейс. Класс `Logger` отвечает **только** за запись логов в файл.
    *   **Результат:** Изменение дизайна интерфейса не затрагивает логику выдачи книг.

*   **O — Open/Closed Principle (Принцип открытости/закрытости)**
    *Суть:* Программные сущности должны быть открыты для расширения, но закрыты для изменения.
    *   **Где применено:** Паттерн **Стратегия (Strategy)** для расчета штрафов. В `LibraryManager` есть переменная `_penalty` типа `IPenaltyStrategy`. Сейчас есть классы `NoPenalty` (без штрафа) и `ProgressivePenalty` (прогрессивный штраф).
    *   **Результат:** Если завтра понадобится добавить новый вид штрафа, мы **не будем менять** код `LibraryManager`. Мы просто создадим новый класс (например, `FixedPenalty`) и передадим его в менеджер.

*   **L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
    *Суть:* Объекты наследующего класса должны без проблем заменять объекты базового класса.
    *   **Где применено:** В иерархии исключений (`Exceptions.cs`). Мы везде ловим ошибки через `catch (LibraryException ex)`. При этом кидаем (`throw`) его наследников: `ReaderNotFoundException`, `DuplicateLoanException`. Программа работает корректно, так как наследники ведут себя предсказуемо.
    *   Также стратегии `NoPenalty` и `ProgressivePenalty` взаимозаменяемы в переменной типа `IPenaltyStrategy`.

*   **I — Interface Segregation Principle (Принцип разделения интерфейса)**
    *Суть:* Клиенты не должны зависеть от методов, которые они не используют.
    *   **Где применено:** В проекте нет одного огромного интерфейса. Вместо этого созданы узкоспециализированные интерфейсы: `ILibraryService` (для библиотеки), `IReport` (для отчетов), `IReportOutput` (для вывода текста), `IBookCsv` (для CSV), `IPenaltyStrategy` (для штрафов).
    *   **Результат:** Классу, который выводит отчет, не нужно реализовывать методы для работы с CSV.

*   **D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
    *Суть:* Зависимости должны быть основаны на абстракциях, а не на конкретных реализациях.
    *   **Где применено:** В файле `Form1.cs` главная форма объявляет переменную так: `private ILibraryService _m;`. Форма **не зависит** от конкретного класса `LibraryManager`. Она зависит только от **интерфейса**.
    *   **Результат:** Мы можем полностью переписать логику менеджера (например, сделать сохранение в облако вместо файла), но форма об этом даже не узнает, и её код не сломается.

### 2.2. Основы ООП
*   **Инкапсуляция:** В классах `Book`, `Reader` и `Loan` свойства доступны через геттеры и сеттеры. Изменение количества доступных книг (`Now`) происходит только через методы менеджера.
*   **Наследование:** Кастомные исключения наследуются от системного класса `Exception`.
*   **Полиморфизм:** Переопределен метод `ToString()` во всех моделях для красивого отображения в `ListBox`. В паттернах используются интерфейсы, что позволяет подставлять разные реализации.

### 2.3. Порождающие паттерны
*   **Singleton (Одиночка):** Класс `Logger` (в `Patterns.cs`). У него приватный конструктор, и он гарантирует, что во всей программе будет только один экземпляр логгера.
*   **Factory Method (Фабричный метод):** Класс `LibraryFactory` и его наследник `DefaultLibraryFactory`. Инкапсулируют создание объектов `Book` и `Reader`.
*   **Builder (Строитель):** Класс `LoanBuilder`. Позволяет пошагово собрать сложный объект `Loan` (Выдача).

### 2.4. Структурные паттерны 
*   **Proxy (Заместитель):** Класс `CachedReport`. Кэширует результат расчета просрочек на 3 секунды, чтобы не пересчитывать тяжелый отчет при частых запросах.
*   **Adapter (Адаптер):** Класс `BookCsv`. Позволяет конвертировать список объектов `List<Book>` в строку формата CSV и обратно.
*   **Bridge (Мост):** Класс `OverdueBridgeReport` (Абстракция) и интерфейс `IReportOutput` (Реализация). Разделяет формирование текста отчета от способа его вывода.

### 2.5. Поведенческие паттерны
*   **Strategy (Стратегия):** Интерфейс `IPenaltyStrategy` и его реализации `NoPenalty` и `ProgressivePenalty`. Позволяет менять формулу расчета штрафа.
*   **Chain of Responsibility (Цепочка):** Классы `BookCheck` и `ReaderCheck`. Реализуют цепочку проверок перед выдачей книги.
*   **Iterator (Итератор):** Класс `LoansByReader`. Позволяет последовательно обходить список выдач конкретного читателя.

### 2.6. Работа с базами данных
*   В проекте используется **Entity Framework 6** (подход Code First).
*   Создан класс контекста `LibraryDbContext`, унаследованный от `DbContext`. В нём объявлены `DbSet` для книг, читателей и выдач.
*   В `Models.cs` применены атрибуты маппинга (`[Table]`, `[Key]`, `[Column]`, `[ForeignKey]`).
*   Метод `SaveToDatabase()` использует `db.SaveChanges()` для сохранения данных в базу без написания SQL.

### 2.7. Тестирование
*   Создан отдельный проект `ДЗ.Tests` с использованием фреймворка **NUnit**.
*   Написаны юнит-тесты, проверяющие бизнес-логику: проверка на дублирование УДК, корректное изменение доступных книг при выдаче и возврате, проверка наличия просрочек. (6 тестов, все проходят).

## 3. Как запустить и протестировать проект

### Требования к системе:
*   Visual Studio 2019 или 2022 (с рабочей нагрузкой «Разработка классических приложений .NET»).
*   .NET Framework 4.7.2.
*   SQL Server LocalDB.

### Инструкция по запуску:
1. Откройте файл решения (`.sln`) в Visual Studio.
2. Нажмите клавишу `F5`. Проект соберется и запустится.
3. При первом запуске программа автоматически создаст тестовые данные.

### Инструкция по запуску тестов:
1. В верхнем меню Visual Studio выберите **Тест** -> **Обозреватель тестов**.
2. В открывшемся окне нажмите кнопку **«Запустить все»**.
3. Все 6 тестов должны быть отмечены зелеными галочками.

## 4. Руководство по использованию

1. **Переключение режимов:** Используйте выпадающий список вверху, чтобы переключаться между «Книгами», «Читателями» и «Выдачами». Поля ввода и список будут меняться автоматически.
2. **Добавление:** В режиме «Книги» заполните поля и нажмите «Добавить». В режиме «Читатели» нажмите «Добавить» — откроется всплывающее окно.
3. **Выдача книги:** В режиме «Книги» выделите книгу и нажмите «Выдать», затем выберите читателя в появившемся окне.
4. **Возврат:** В режиме «Выдачи» выберите активную выдачу и нажмите «Вернуть».
5. **Отчет:** Нажмите «Отчёт», чтобы увидеть список просроченных книг и сумму штрафа.
6. **Сохранение:** При закрытии программы нажмите «Да», чтобы сохранить данные в файл и базу данных.

## 5. Обоснование отсутствия паттерна Abstract Factory

Паттерн **Abstract Factory (Абстрактная фабрика)** в проекте не используется, и это обоснованное архитектурное решение:
1.  **Отсутствие семейств объектов:** Абстрактная фабрика нужна для создания взаимосвязанных семейств объектов (например, кнопок и окон для разных ОС). В нашей предметной области сущности `Book` и `Reader` независимы.
2.  **Принцип KISS (Keep It Simple, Stupid):** Внедрение этого паттерна стало бы избыточным усложнением кода.
3.  **Достаточность Factory Method:** Использованный паттерн «Фабричный метод» полностью решает задачу создания объектов и легко расширяется при необходимости.
